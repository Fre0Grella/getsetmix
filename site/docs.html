Documentation

GetSetMix is a single-container FastAPI service with a vanilla-JS UI. State lives in SQLite under the data directory; downloads land directly in your music library; finished tracks are appended to a rekordbox.xml you import once in Rekordbox — one XML per machine, each carrying paths valid on that machine.

Use GetSetMix only for content you have the rights to download.

Docker Compose

# deploy/docker-compose.yml — edit the music path first
services:
  getsetmix:
    image: ghcr.io/Fre0Grella/getsetmix:latest
    ports: ["8765:8765"]
    volumes:
      - getsetmix-data:/data
      - /path/to/your/music:/music
    environment:
      GSM_LANGUAGE: en            # or it
      # GSM_AUTH_TOKEN: change-me # enable if exposed
volumes:
  getsetmix-data:
docker compose -f deploy/docker-compose.yml up -d
# open http://localhost:8765

The image bundles ffmpeg and runs as a single process well under 1 GB of RAM. /data holds the SQLite database, config, covers and the default XML; /music is your library root — files are written straight into it.

Kubernetes

Plain manifests live in deploy/k8s/getsetmix.yaml: a namespace, a ConfigMap, PVCs for data and music, a Deployment with liveness/readiness probes and Prometheus scrape annotations, and a Service. An Ingress example is included commented out.

kubectl apply -f deploy/k8s/getsetmix.yaml
kubectl -n getsetmix get pods
  • replicas: 1 with strategy: Recreate is intentional — state is SQLite on a PVC, so never scale this Deployment.
  • Replace the music PVC with hostPath or NFS if your library already exists on a node or NAS.
  • Images are published multi-arch (amd64 + arm64) to GHCR by the release workflow, so it runs on a Pi-based cluster too.

Local app mode

For a laptop next to your controller — starts the server and opens the browser, like a desktop app. Prebuilt executables for Windows, macOS and Linux are attached to every GitHub Release (no Python needed; data lives in ~/.getsetmix, ffmpeg still required on PATH). Or run from source:

pip install -r requirements.txt
# ffmpeg must be on PATH:
#   Linux: apt install ffmpeg · macOS: brew install ffmpeg · Windows: winget install ffmpeg
python run_local.py             # opens http://127.0.0.1:8765
python run_local.py --port 9000 --no-browser

Daily workflow

  1. Paste link — the URL on your clipboard is added. Playlists fan out into one editable row per entry; duplicates of URLs you've already ingested are flagged.
  2. Rows resolve metadata in the background. Fix title and artist (both required), pick a genre from the DJ-oriented list, optionally set album. The camera button on the artwork opens cover search and upload.
  3. Download starts the batch. The ×N selector next to it overrides download parallelism for this batch only (the global default is 2). Edits lock once a track is queued.
  4. Watch per-track states and the batch bar. Cancel download stops in-flight tracks and returns them to staged. A failed track shows its error and a retry button — the rest of the batch continues.
  5. When tracks show Done, refresh the rekordbox xml tree in Rekordbox and find them in the Inbox playlist.

Rekordbox setup

Run the setup wizard once — open http://<server>:8765/setup from the machine that has Rekordbox. It is served by the server, but it is meant to be read from there: the paths it shows are the ones you paste into Rekordbox.

  1. Library — where downloads land on the server. Under Docker this is the path inside the container (usually /music), not the path on your NAS.
  2. Delivery — how the files reach the DJ machine: the same machine · a folder Nextcloud or Syncthing already syncs · uploaded to Nextcloud over WebDAV (no mount, no sync client on the server — the right answer under Docker and Kubernetes) · an SMB/NFS share.
  3. DJ machine — pair the companion, or type the library folder as that machine sees it. Either way you get a live preview of the exact Location string the XML will contain, before you commit to it.
  4. Verify — library writable, XML valid, sampled paths actually resolving, collection export present and current, companion reachable. Anything that fails tells you what to do about it.

Then in Rekordbox: Preferences ▸ Advanced ▸ Database ▸ rekordbox xml → the path the wizard shows. Enable the rekordbox xml source in the sidebar, and refresh that tree after each batch — nothing can make Rekordbox reload it automatically, so that click stays yours.

Why this used to break

Earlier versions stamped the server's absolute path into every Location. The server's truth is /music/…; Rekordbox's is C:\Users\you\Nextcloud\Music\…. Nothing reconciled the two, so tracks imported as missing files and no setting could fix it.

Now a track's identity is its path relative to the library root. Each machine gets a profile recording its own view of the library, and its own XML with paths valid there:

MachineIts view of the same track
server/music/Hardstyle/Artist - Title.mp3
studio PCC:\Users\marco\Nextcloud\Music\Hardstyle\Artist - Title.mp3
laptop/Users/marco/Music/Hardstyle/Artist - Title.mp3

Add a profile per machine and each gets its own XML, so a Windows desktop and a macOS laptop share one library without either seeing the other's paths.

The writer stays conservative: it appends with incrementing TrackIDs, writes atomically, and if the XML on disk is ever corrupt it backs it up as *.corrupt.xml and starts a fresh one rather than failing the batch.

The status chip

The chip in the toolbar re-runs those same checks every minute, so a link that breaks later — a stale collection export, a sync that stopped, a library root that moved — says so in the app instead of waiting for a red icon in Rekordbox. Click it for the full list.

The companion

Optional, recommended. One stdlib-only file on the machine with Rekordbox:

curl -fsSLO http://<server>:8765/link/gsm_link.py
python3 gsm_link.py detect
python3 gsm_link.py pair --server http://<server>:8765 --code 123456
python3 gsm_link.py doctor
python3 gsm_link.py run

It answers what the server cannot see from the other side of a sync folder: where Nextcloud or Syncthing actually put the library (read from the sync client's own config, so you never type that path), and whether the XML's paths open real files on that machine. It is headless — everything it finds shows up in the web UI.

Its --apply flag will update Rekordbox's XML path preference, but only when it finds an option that already exists and already holds an .xml path. That config format is undocumented and changes between versions, so rather than guess a key it reports manual and the wizard shows you the path to paste. Close Rekordbox first; the original file is backed up.

Nextcloud over WebDAV

Choosing WebDAV delivery makes the server push each finished file — and the XML — straight into Nextcloud with an app password. No mount, no sync client next to the server, which is exactly what made this awkward in a container before. The remote path then becomes the shared language between the two machines, and the companion resolves it to a local folder from the sync client's config, so neither side has to agree on an absolute path.

Keeping the inbox clean with your collection XML

Export your full collection from Rekordbox (File ▸ Export Collection in xml format) and set its path as Rekordbox collection XML. Before each batch, GetSetMix compares the inbox XML against the collection — matching by source URL, file location, or normalized title + artist — and removes tracks you've already imported. The Inbox playlist then only ever lists songs still missing from your collection, instead of growing forever. Health warns when that export goes stale, since a 6-month-old one quietly defeats the whole thing.

Filename templates

Set the template in Settings or via GSM_FILENAME_TEMPLATE. Available tokens:

TokenValue
{title}Track title (after your edits)
{artist}Artist
{album}Album, omitted when empty
{genre}Genre, omitted when empty
{source}Source site, e.g. youtube
{id}Source video/track ID

Illegal filesystem characters are stripped, separators left behind by empty tokens are collapsed, and name collisions get a (2)-style suffix with a warning on the track.

Configuration

Everything is editable from the gear icon and persisted to <data>/config.json. Machine profiles live in the same file and are managed by the setup wizard rather than by environment variables. Environment variables override on boot:

Authentication

GetSetMix is private by default — run it on your LAN or tailnet with no auth. If you expose it, set either a static token or Basic credentials. With auth enabled, the API and /metrics return 401 without credentials; the UI asks for the token once and keeps it in the browser.

# any of these work with GSM_AUTH_TOKEN=sekret
curl -H "X-Auth-Token: sekret"        http://host:8765/api/tracks
curl -H "Authorization: Bearer sekret" http://host:8765/api/tracks
curl "http://host:8765/metrics?token=sekret"   # for Prometheus scrape_configs

Metrics

GET /metrics serves Prometheus text format. The Kubernetes manifests already carry scrape annotations.

getsetmix_jobs{status="staged|queued|downloading|tagging|ingested|error|…"}
getsetmix_active_downloads
getsetmix_download_duration_seconds_sum / _count
getsetmix_errors_total{source="youtube|soundcloud|…"}
getsetmix_songs_downloaded{window="30d"|"365d"|"all"}
getsetmix_healthy

Handy Grafana starters: songs per month from getsetmix_songs_downloaded, error rate by source, and average download time from the duration sum/count pair.
